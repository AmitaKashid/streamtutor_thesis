# Context study protocol

This runner prepares a controlled study; it does not establish that the draft questions are representative or that model answers are correct. Review and expand the cases before using the results for a thesis. The four synthetic examples in `data/context_study/draft_cases.jsonl` are a starting point only. Include multiple subject areas, independent dialogues and both standalone questions and follow-ups whose necessary evidence is 1, 3 or 5 turns back. Review each question, all five turns, fixed RAG evidence, reference and the claimed required distance; prevent the answer from leaking into more recent turns or RAG. Fill `reviewed_by` only after review. Do not use real student data without appropriate authorization.

Make a manifest JSON with nonempty `model_filename`, `model_sha256`, `gpu`, `server_version`, `server_configuration`, `load_description`, and `reviewer`. Record the GGUF hash and hardware/version/settings from the actual remote server, not a local copy. The runner verifies the server's reported filename and health; manifest fields are self-reported and must be checked independently. Record exclusive GPU access/load, context window, slots, model quantization and exact server launch command. Repeat the same protocol with each model and record differences. Identical settings cannot eliminate differences in model architecture, tokenizer or hardware.

Example, after creating reviewed inputs:

```
.venv\Scripts\python.exe scripts\context_diagnostics\context_study.py --url http://127.0.0.1:18090 --cases reviewed_cases.jsonl --manifest llama_manifest.json --output context_study_llama.jsonl --repetitions 3
.venv\Scripts\python.exe scripts\context_diagnostics\review_context_study.py --input context_study_llama.jsonl --output context_study_llama_review.csv
```

The 0, 1, 3, 5-turn policies are paired for each question. The runner randomizes conditions and records prompt hash, token and latency fields, model endpoint identity, settings, output and completion status. Thinking is requested off, with temperature zero and a 1024-token output cap by default. Confirm the server supports and honors these settings. A length finish, stream error, unexpected reasoning, missing counters, or failed cache prime invalidates that row; increase the cap and rerun the whole affected design when truncation occurs. Cache-on primes the identical prompt immediately before measurement; cache-off is requested, not independently guaranteed. Check actual cached counts and do not compare cache conditions when they contradict the protocol. Priming also changes GPU warmth; report that limitation.

For each complete response, independently label correct recall, appropriate clarification when required evidence is missing, and false denial when evidence is present as yes, no or not-applicable. Use the exact history and RAG shown in the review CSV. Have a second reviewer assess a sample independently and resolve disagreements. The review CSV hides history limit, model, trial and timing fields but an experienced reviewer may infer conditions from the history text. Review IDs are the first 16 hex characters of SHA-256 of `seed:zero_based_input_row`; this joins a reviewed row to its original JSONL record. Never use incomplete rows as quality successes or failures. Report quality and latency together per condition, with counts, variability and incomplete rates. Treat repeated generations of the same case as clustered, not independent questions. This study needs substantially more reviewed cases than the four drafts for a defensible result.
